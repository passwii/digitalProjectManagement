# 应收应付手工指定与拆分核销设计

## 目标

在财务工作台现有收款/付款操作中增加手工指定核销单据的能力：一笔收付款可全部核销到一张往来单，也可按金额拆分到同一主体、同一往来科目下的多张单据。现有 FIFO 自动分配作为默认方式保留。

本阶段仅处理应收应付工作台登记的往来单据，不改变普通凭证、期初辅助余额的报表范围；新建账套继续只使用人民币 CNY，不引入多币种或汇率。

## 方案选择

1. **推荐：扩展现有收付款接口和弹窗。** 可选传入目标单据与核销金额；不传则延续 FIFO。无需迁移，旧 API 调用保持兼容。
2. 收付款过账后再单独创建核销分配：会在凭证过账与核销之间留下未分配状态，并增加二阶段失败恢复逻辑，不符合当前“保存即占用核销额”的生命周期。
3. 完全替换 FIFO 为手工分配：会改变现有行为并要求所有 API 调用端同步升级，没有必要。

采用方案 1。

## 业务规则

- 未提供 `allocations` 时，继续按当前账套、应收/应付类型、主体、往来科目、已过账状态和凭证日期使用 FIFO。
- 提供 `allocations` 时，按明细指定核销目标。每个目标最多出现一次；金额必须大于零且最多两位小数；至少指定一条；核销金额之和必须等于本次收付款金额。
- 目标单据必须属于当前账套、同一应收/应付类别、同一客户/供应商和同一往来科目；目标凭证须已过账、日期不得晚于收付款日期，且原单不能处于冲销中或已冲销状态。
- 每笔核销金额不得超过目标单据当前可核销余额。后端重新读取并锁定候选目标行后校验，前端显示仅作帮助，不作为权限或金额校验边界。
- 多个目标行按 `(transaction_date, id)` 顺序加锁，与 FIFO 路径保持一致，降低并发死锁风险；同一目标余额由行锁保护，避免并发收付款超额核销。
- 成功时仍创建待审核收付款草稿凭证，并立即登记 `ARAPAllocation`、占用目标未核销余额；删除/作废/冲销释放继续复用现有生命周期，不新增数据表或迁移。
- 不支持超额收款/付款、未分配余额、预收/预付及跨主体或跨往来科目核销。

## API 契约

现有 `/finance/receivable-collections` 和 `/finance/payable-payments` 请求增加可选字段：

```json
{
  "allocations": [
    {"target_id": 101, "amount": "60.00"},
    {"target_id": 102, "amount": "40.00"}
  ]
}
```

- `target_id` 指向 `ARAPTransaction.id`；路由类型决定它代表应收或应付。
- 不传字段表示旧版 FIFO 行为。传入空数组、重复目标、金额合计不等于支付金额或不合资格的目标均返回结构化 400，不创建凭证或分配记录。
- 响应继续返回实际分配明细与草稿凭证，不改变既有返回字段。

## 界面交互

- 收付款弹窗增加“按单据日期先进先出”和“指定单据”两种方式，默认 FIFO。
- 指定模式列出同主体、同科目、截至所选收付款日期可核销的已过账单据，显示凭证号、日期、摘要、剩余金额和本次核销金额输入。
- 页面实时显示本次收付款金额、已分配金额及差额；金额未全部分配、超出单据余额或无合格目标时禁用提交并说明原因。
- 保存后继续提示草稿凭证待审核/过账及核销金额已占用；接口错误保留输入值并显示中文业务错误。

## 验收与测试

- API 测试覆盖应收/应付的单据内部分核销和一笔收付款拆到多张单据；不传 `allocations` 时已有 FIFO 测试继续通过。
- API 测试覆盖跨主体、跨科目、未过账、日期晚于收付款、冲销中、已冲销、重复目标、空明细、合计不等及超额核销；错误后不产生凭证/分配，也不改变 `applied_amount`。
- 并发校验复用按稳定顺序锁定目标行的实现；回归用例确认相同目标不能超额分配。
- DOM 测试覆盖方式切换、候选单据筛选、分配金额合计、提交 payload 与提交禁用状态。
- 不新增数据库迁移；财务金额保持 CNY 的两位小数十进制字符串。

## 暂不包含

- 预收预付、超额收付款、手工释放单笔核销、普通手工/模板/导入凭证核销及期初辅助余额导入。
- 将当前工作台报表扩展为完整往来辅助明细账；该口径需单独阶段设计和验收。
