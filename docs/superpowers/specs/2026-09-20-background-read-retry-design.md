# 前端读取请求后台恢复设计

## 1. 背景与目标

在网络质量较差、短暂丢包或后端瞬时不可达时，当前前端会把读取请求失败直接呈现为“API 不可用”“加载失败”或“加载信息未完全”。这会清空部分页面数据，并要求用户手动点击重试。

本次设计的目标是：

- 读取请求失败后由前端后台持续恢复，不要求用户反复操作。
- 已经展示的数据继续保留，不因短暂网络抖动变成空白或错误页。
- 网络恢复、页面重新获得焦点或从后台回到前台时及时重试。
- 不让短暂断联变成强烈的错误提示或 Toast。
- 保留首次加载的正常骨架态，并在后台恢复期间维持稳定布局。
- 写入请求不进行无条件无限自动重试，避免重复创建、重复审批、重复删除和重复上传。

## 2. 当前实现与问题边界

前端读取请求主要经过 `web/lib/useAsyncData.ts`，页面失败状态由 `web/components/ui/PageState.tsx` 的 `LoadFailed` 展示。当前请求失败路径会同时设置错误并清空数据：

```text
读取失败 -> setError(...) -> setData(null) -> 页面显示 LoadFailed
```

这套行为适合明确告诉用户“本次加载失败”，但不适合处理短暂网络抖动。当前项目同时存在权限同步、移动端抽屉、项目范围探测和上传队列等独立数据流，因此本次变更应优先收敛在通用读取 Hook，不把相同 retry 逻辑复制到每个页面。

写入请求包括登录、新建、编辑、删除、审批、进度提交、附件上传和导出等操作。这些操作在网络超时后可能已经在服务端成功，浏览器只是没有收到响应；自动重放可能造成重复业务结果。因此写入请求继续沿用现有明确失败和手动处理语义。

## 3. 方案

### 3.1 读取请求统一后台 retry

扩展 `useAsyncData`，让 GET 读取请求默认具备后台恢复能力。每次依赖变化或手动 `reload()` 都创建独立的请求生命周期；请求失败后进入退避重试，成功后更新数据并清理错误状态。

可自动恢复的失败类型：

- 网络异常和连接失败。
- HTTP `408`、`425`、`429`。
- HTTP `500`、`502`、`503`、`504`。

不进入无限后台 retry 的类型：

- `400`：请求参数或业务输入错误。
- `401`：交给现有会话失效和登录跳转逻辑。
- `403`：权限不足。
- `404`：资源不存在。
- 其他明确业务错误。

### 3.2 退避节奏

后台重试使用指数退避并设置上限：

```text
第 1 次失败：约 1 秒后
第 2 次失败：约 2 秒后
第 3 次失败：约 4 秒后
第 4 次失败：约 8 秒后
后续失败：不超过约 30 秒一次
```

每次延迟加入小幅随机抖动，避免多个页面或多个浏览器同时恢复时形成请求尖峰。组件卸载、依赖变化、手动 reload 或 `AbortController` 取消时，必须清理等待中的 timer 并停止旧请求的后续 retry。

### 3.3 保留旧数据

当已有数据时，读取失败不得再执行 `setData(null)`。失败期间：

- 保留当前列表、卡片、详情或权限数据。
- 不渲染页面级 `LoadFailed`。
- 不弹出“API 不可用”类 Toast。
- 后台继续 retry。
- 成功后直接替换为新数据。

这样用户看到的是最近一次成功的数据，而不是因短暂断联出现的空白状态。`error` 仍可作为内部状态或低干扰同步状态的来源，但不应再让已有数据页面进入强错误态。

当尚无任何数据时：

- 继续显示现有 `LoadingBlock`。
- 自动后台 retry。
- 不立即显示强烈的错误页。
- 可在全局或首屏加载区域提供低干扰的“正在同步数据…”状态，但不能覆盖页面主要内容或造成布局跳动。

### 3.4 网络与页面生命周期触发即时恢复

在通用读取恢复层增加浏览器事件监听：

- `window` 的 `online` 事件：立即触发一次 retry。
- `document.visibilitychange` 从隐藏恢复为可见：触发一次 retry。
- `window` 的 `focus` 事件：在当前请求不在途时触发一次 retry。

这些事件不能产生重复并发请求。正在请求时只保留一次待处理信号，当前请求结束后按最新状态决定是否继续执行。

### 3.5 全局状态与用户感知

本次不增加阻塞式全屏 Loading。全屏 Loading 会让用户在网络波动时无法继续查看已经加载的数据，反而放大断联感知。

推荐增加轻量、非阻塞的全局同步状态，仅在必要时使用：

- 首次加载时由现有页面骨架表达加载中。
- 已有数据且后台 retry 时不显示明显错误；如需要可在顶栏或活动指示区域显示低对比度的“正在同步”状态。
- 恢复成功后自动收起，不弹成功 Toast。
- 写操作失败继续使用现有明确错误文案和手动重试入口。

该状态必须是辅助信息，不能遮挡内容、锁定页面或阻止用户导航。

## 4. 数据流与状态语义

```text
依赖变化 / reload / online / 页面回前台
        |
        v
   发起 GET 请求
        |
   +----+----------------+
   |                     |
 成功                  可恢复失败
   |                     |
 更新 data          保留旧 data
 清理 error         进入退避 retry
   |                     |
   +-----------> 成功后更新 data

不可恢复失败 / 401 / 403 / 404
        |
        v
 按现有业务错误语义处理
```

`useAsyncData` 的公开返回值保持兼容：`data`、`loading`、`firstLoad`、`error`、`reload`、`setData` 均继续存在。必要时只增加内部状态或可选的非破坏性字段，例如是否正在后台恢复；已有页面不应被迫逐个重写。

## 5. 并发、取消与一致性约束

- 同一个 Hook 实例最多只能存在一个在途读取请求和一个等待中的 retry timer。
- 依赖变化时取消旧请求，旧请求和旧 timer 都不能修改新依赖对应的数据。
- 手动 `reload()` 应取消旧 retry 链并从新的退避序列开始。
- `AbortError` 不应被记录为网络失败，也不应触发 retry。
- `401` 仍由现有 `clearSession()` 和登录跳转逻辑处理，不应被后台 retry 掩盖。
- 读取数据可以短暂保持旧值，但写入成功后的页面刷新必须能通过新的读取请求最终收敛到服务端状态。
- 不能把 POST、PATCH、DELETE、XHR 上传等写操作接入本次无限 retry 机制。

## 6. 测试设计

实现前先为通用恢复逻辑增加失败测试，至少覆盖：

1. 网络失败后会自动 retry，并在后续成功时返回数据。
2. retry 延迟逐步增加，且不会超过上限。
3. 已有数据时请求失败不会清空数据。
4. 后台恢复成功后会替换旧数据并清理错误状态。
5. `400`、`401`、`403`、`404` 不会进入无限 retry。
6. `500`、`502`、`503`、`504` 和网络错误会进入 retry。
7. `online`、页面回前台和 focus 能触发即时恢复。
8. 组件卸载、依赖变化和 Abort 后不会继续执行旧 retry。
9. 同一 Hook 不会因为多个生命周期事件产生并发重复请求。
10. 现有写操作和上传错误测试保持原有失败语义。

重点验证命令：

```text
cd web
npm run test:unit
npm run test:motion
npm run build
```

## 7. 影响范围与非目标

预期影响范围：

- `web/lib/useAsyncData.ts`：统一读取 retry、退避、取消和生命周期恢复。
- `web/lib/api.ts`：必要时提供结构化的可重试错误判定，避免依赖错误文案。
- 通用测试文件：固定 retry 和保留旧数据行为。
- 如确有必要，增加一个轻量同步状态组件和对应样式。

本次不包含：

- 写操作无限自动重试。
- 离线写入队列或本地事务缓存。
- 数据库、API worker、反向代理或连接池改造。
- 页面业务接口逐个重写。
- 将旧数据标记为“实时有效”；后台恢复期间它只是最近一次成功快照。

## 8. 验收标准

- 网络短暂失败时，已有页面内容不消失。
- 用户无需点击“重试”，网络恢复后页面数据能够自动更新。
- 首次加载失败时页面保持稳定加载态，不频繁闪烁错误页。
- 不会因为 retry 产生多个并发 GET 请求。
- 不会对写操作进行无感知重复提交。
- 会话失效和权限错误仍然按原有逻辑处理。
- 单元测试、前端测试和生产构建通过。
