# 设备报废 / 作废二次确认设计

> 日期：2026-09-28
> 范围：设备详情抽屉中的「报废」和「作废」终态操作

## 背景

设备状态机将 `scrapped`（已报废）和 `void`（已作废）定义为终态：没有后续恢复动作，且这两个状态下也禁止编辑档案。误操作后目前只能由管理员永久删除设备和流水，再重新建档。现有详情页按钮会直接调用状态变更接口，缺少确认步骤。

## 决策

1. 点击「报废」或「作废」时，先打开应用内二次确认窗口；只有点击窗口中的最终确认按钮才提交状态变更。
2. 窗口提供「取消」和明确的「确认报废」/「确认作废」操作；不要求输入关键词。
3. 确认窗口展示设备编号、名称、当前状态和操作后果。
4. 报废文案明确指出进入「已报废」后不能恢复或编辑档案；作废文案明确指出进入「已作废」后不能恢复或编辑档案。
5. 作废可从已领用或借用中状态发起，因此当当前状态为 `claimed` 或 `borrowed` 时，窗口额外提示确认后系统会清空使用人和到期日。其他起始状态不显示该提示。
6. 「送修」不增加确认；维修状态可以通过「恢复可用」撤回。
7. 二次确认是前端防误点措施，不改变后端状态机、权限、API、审计事件或数据库结构。

## 交互与实现范围

在 `web/app/(dashboard)/assets/page.tsx` 的 `AssetDetail` 内维护待确认操作（`scrap` / `void` / `null`）。原有「报废」和「作废」按钮只设置待确认操作，不再直接调用 `onAction`。复用项目现有 `Dialog`，展示与所选操作对应的标题、警告、设备信息和后果；取消或关闭窗口清除待确认状态；最终确认时调用原 `onAction(action, { note })`，状态提交中的 `busy` 状态禁止重复确认。

视觉样式沿用设备页现有危险操作颜色和通用对话框，不新增全局组件或依赖。

## 验收与测试

- 点击「报废」后，确认窗口出现，API transition 尚未调用；取消后窗口关闭且无请求。
- 确认报废后，调用 `transition(assetId, "scrap", { note })` 一次。
- 点击「作废」后，显示不可恢复 / 不可编辑说明；若起始状态为已领用或借用中，也显示清空使用人和到期日的提示。
- 确认作废后，调用 `transition(assetId, "void", { note })` 一次；取消不提交。
- 两个确认窗口显示设备编号、名称和当前状态；确认按钮操作名称清晰，busy 时不可重复提交。
- 维修流程保持原样：送修仍直接执行，维修中仍可恢复可用。
- 运行资产页面 DOM 测试及相关前端测试；后端无改动，无需数据库迁移。

## 非目标

- 不增加终态的撤销 / 恢复 API。
- 不修改报废、作废的后端转换许可、权限和审计结构。
- 不为送修、恢复可用、领用、借用、归还增加二次确认。
- 不要求输入关键词，不改变强制删除流程。
