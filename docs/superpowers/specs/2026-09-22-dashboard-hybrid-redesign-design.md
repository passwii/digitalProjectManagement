# Dashboard 混合科技工作台设计规格

## 一、设计目标

将登录页已经确认的「科幻身份握手」视觉语言延展到 Dashboard，但不把日常运营页面做成难以阅读的全屏特效页。最终采用「深色科技外壳 + 高可读工作面」的混合方案：

- 深色导航、顶栏和少量状态装饰负责建立产品识别度与科技感。
- 浅色内容工作区负责承载指标、图表、表格和编辑入口，保证长期使用时的扫描效率。
- 保留现有数据结构、table Layout、Dialog 编辑习惯和移动端导航行为，只对层级、密度、反馈和动效做系统化打磨。
- 所有信息都来自现有 Dashboard 数据，不新增没有数据来源的“趋势”“增长”或模拟实时指标。

## 二、使用场景与成功标准

Dashboard 的主要用户包括项目负责人、项目执行人员、财务与审批人员及管理员。页面需要支持他们在一次打开后快速完成三件事：

1. 了解当前项目、逾期任务、审批/通知和当月支出的关键状态。
2. 发现项目健康度、支出结构和本周动态中的异常或待处理事项。
3. 继续进入既有 table 和 dialog 流程完成查看、筛选、审批和编辑，不需要重新学习交互方式。

成功标准：

- 首屏层级明确，用户可以先看 KPI，再看风险与异常，最后进入明细。
- 科技感来自色彩、细线、状态指示和克制的动效，而不是持续闪烁、复杂背景或遮挡信息。
- 刷新、加载、空状态、失败、成功和 reduced-motion 状态都有明确反馈。
- 桌面端不牺牲信息密度，平板和移动端不出现横向溢出或不可操作的控件。
- 表格仍然是表格，编辑仍然通过现有 Dialog/Drawer/Confirm 组件完成。

## 三、视觉方向

### 3.1 色彩与表面

采用现有全局设计变量作为基础，并在 Dashboard 范围内补充科技主题语义，不直接覆盖全站基础色：

- 外壳深色：沿用 `--navy`，可使用接近 `#07131f` / `#0b1b29` 的深蓝层级。
- 科技强调：青色 `#6cf3ff` 用于焦点、运行中状态、细线和少量装饰；荧光绿 `#c6ff72` 用于完成/健康状态和关键正向反馈。
- 风险色：沿用现有 danger/warn 语义，橙色或珊瑚色只用于逾期、待处理等需要注意的状态。
- 工作面：保留浅灰背景和白色卡片，让表格、数字与输入控件保持高对比度。
- 线条：优先使用 1px 边界和内嵌高光，避免大量厚重阴影；卡片保持现有紧凑圆角体系，不引入大面积胶囊化。

状态必须同时通过文字、Badge、图标或结构传达，不能只依靠颜色。科技强调色只承担识别和引导，不改变业务语义。

### 3.2 字体与信息密度

- 页面标题保持清晰、克制的无衬线字重，不引入展示型字体或只适合英文的窄体。
- Dashboard 正文与关键控件不低于现有可读性基线；核心 KPI 数字保持较大字号，辅助标签和时间信息适度提升，避免出现登录页中已经修正过的小字问题在 Dashboard 重现。
- 数据数字使用等宽数字特性或稳定的数字宽度，避免 CountUp 过程中布局跳动。
- 通过标题、标签、数值、辅助说明四级层级组织内容，不依赖过多颜色和装饰。

### 3.3 科技感的使用边界

- 外壳可使用极低对比度的网格、扫描线或状态光晕，但必须位于背景层，不干扰正文。
- 不新增登录页已经移除的「轨道扫描场」或类似中心雷达动效。
- 不使用持续高频闪烁、自动轮播或会把用户注意力从异常数据上移开的背景动画。
- 动效服务于状态变化与空间关系，不能把页面做成演示动画。

## 四、信息架构与页面结构

保留当前 Dashboard 的四段结构与数据来源，顺序不变：

### 4.1 工作台页头

- 继续使用 `PageHeader`，标题为「工作台」。
- 保留「刷新」和管理员可见的「待审批」入口。
- 页头视觉上与深色外壳建立连接，但操作区仍保持浅色工作面上的清晰按钮样式。
- 刷新进行中时，按钮进入轻量进行中状态并防止重复触发；已有内容不被清空。

### 4.2 四项 KPI

保留当前四项指标及权限分支：

- 我的项目：项目总数与进行中数量。
- 逾期任务：逾期总数与本人负责数量。
- 待我审批或未读通知：根据权限显示现有业务指标。
- 当月支出：当前月份支出与项目数量。

KPI 使用 Dashboard 专属的 `DashboardMetricCard`（名称可在实施阶段微调）统一结构：标签、主数值、辅助说明、状态标识和可选的轻量状态线。组件只负责表现与状态，不计算新的业务指标。

### 4.3 图表区

保留两个现有图表：

- 近 6 个月支出趋势：维持折线图表达，并强化标题、坐标轴、Tooltip 和关键点的可读性。
- 人员支出构成：维持环形图表达，并让图例、数值和颜色映射更容易对应。

图表卡片统一标题区、数据区和加载/空状态处理；不引入新的图表类型，不用动效掩盖数据缺失。

### 4.4 项目健康度与本周动态

- 项目健康度继续使用现有 table Layout，保留项目链接、状态 Badge、加权进度、完成率和逾期信息。
- 本周动态继续使用时间线/分组列表表达，保留逾期、即将到期、进度日志三类现有内容。
- 两块内容在桌面端并列，在窄屏堆叠；健康度表格保持可横向滚动，而不是压缩到无法阅读。

## 五、组件边界与代码范围

### 5.1 Dashboard 专属组件

优先新增以下 Dashboard 范围内组件或样式模块，避免把业务特例扩散到全局：

- `DashboardMetricCard`：统一 KPI 卡片的结构、状态和数值动效。
- Dashboard 页面样式模块：统一布局、图表卡片、健康度表格、动态时间线、刷新状态和响应式规则。

组件应通过明确的 props 表达标签、主值、辅助值、语义 tone 和可选状态，不在组件内部写死权限或 API 判断。

### 5.2 共享组件

继续复用并只做视觉层升级：

- `PageHeader`
- `Badge`
- `ProgressBar`
- `TableToolbar`
- `Modal` / `Drawer` / `Confirm`
- `Empty`
- `MotionStagger`、`CountUp` 及现有 reduced-motion 能力

共享组件的改动限于 token、边界、间距、状态样式和过渡表现；不改变既有 props、键盘行为、焦点管理、脏表单确认或关闭语义。若 Dashboard 需要额外选择器，优先通过页面作用域或 `data-*` 属性隔离。

### 5.3 外壳与其他页面的影响

- Dashboard 可以使用页面作用域对 `Shell` 顶栏建立更明确的深色科技连接。
- 不把 Dashboard 的深色内容面或特殊动画推广到所有业务页面。
- 不修改 API、权限规则、路由结构、表格数据字段或现有 Dialog 表单字段。
- 其他页面只应获得不破坏兼容性的共享基础样式改进。

## 六、状态与交互行为

### 6.1 首次加载

- 首次进入且没有数据时，使用现有 `LoadingBlock` 体系展示与最终布局相近的骨架。
- 骨架不做高频闪烁；使用低对比度呼吸或静态状态，并遵守 reduced-motion。
- 失败时显示可读的错误提示和重试入口，不留下无限加载状态。

### 6.2 刷新

- 已有数据时刷新不清空 KPI、图表、表格和动态内容。
- 页头按钮、页面 `aria-busy` 和现有活动指示器提供轻量刷新反馈。
- 刷新成功后只对发生变化的数值和状态做短暂提示，不让整个页面重新播放入场动画。
- 刷新失败时保留最后一次成功数据，并显示“数据可能已过期”的可理解提示与重试入口。

### 6.3 空数据与异常

- 继续使用 `Empty`，区分“暂无数据”和“加载失败”。
- 图表无数据时保留图表卡片的标题和结构，避免页面跳动。
- 部分 weekly 数据失败时，其他已成功的 Dashboard 区块仍可用；不因辅助数据失败而遮蔽主数据。

### 6.4 Table 与 Dialog

- table 仍承担批量浏览、排序/筛选和进入详情的职责。
- Dialog/Drawer 仍承担编辑、审批确认和补充信息的职责。
- 保留 Escape 关闭、焦点回收、滚动锁定、脏表单二次确认和 Confirm 阻断行为。
- 打开 Dialog 时使用统一的短距离进入动效；保存成功时以按钮状态、Toast 或现有成功反馈表达结果，不让弹窗突然消失后无解释。

## 七、动效规范

### 7.1 页面进入

- 页面结构使用一次性轻量 reveal：页头、KPI、图表、下方内容按信息层级错峰出现。
- 推荐使用现有 `MotionStagger`，时长约 160–220ms，错峰间隔保持克制；不对每一行表格做级联动画。
- 首次进入动画不能阻塞键盘操作或数据读取。

### 7.2 数据动效

- KPI CountUp 只在初次展示或数值真正变化时运行，使用现有能力并控制在短时长内。
- 图表保留 Recharts 的轻量绘制动画；Tooltip、图例和坐标轴不做额外弹跳。
- 进度、Badge 和表格状态变化使用颜色/宽度/透明度的短过渡；不让布局频繁 reflow。
- 刷新不触发全页入场动画，避免用户失去当前阅读位置。

### 7.3 交互反馈

- 按钮、链接、表格行和可点击卡片使用明确 hover/focus/pressed 状态。
- Dialog 使用现有 AnimatePresence 结构，统一进入、退出和背景层过渡。
- 所有动画在 `prefers-reduced-motion: reduce` 下退化为即时切换或极短淡入，内容和操作顺序不改变。

## 八、响应式规则

- 桌面端：KPI 保持四列；图表两列；健康度与本周动态两列。
- 平板：KPI 根据可用宽度折成两列；图表和下方内容逐步堆叠，保留足够卡片内边距。
- 移动端：单列内容；继续使用现有 `MobileDock` 与 `DashboardSheet` 习惯；不新增依赖 hover 的操作。
- 健康度 table 使用现有滚动容器和清晰的最小列宽；标题、状态和数值不能被截断到无法理解。
- Dialog/Drawer 继续遵循共享组件的移动端全屏或底部抽屉规则，不另起一套 Dashboard 弹层。

## 九、可访问性与性能

- 使用真实的 `h1`/`h2` 层级、表头、按钮和链接；不以 div 模拟交互控件。
- 刷新区域提供 `aria-busy`，错误和成功反馈使用现有可访问通知方式。
- 保证深色外壳文字、浅色工作面文字、焦点环和状态文字达到可读对比度。
- 颜色只是辅助，不作为唯一状态信息。
- 优先使用 transform/opacity 过渡，避免动画触发布局抖动；不在数据量大的 table 上添加逐行持续动画。
- 保持当前 API 请求并发方式；刷新时不额外发起重复请求或引入轮询。

## 十、实施验证

实施完成后至少验证以下内容：

1. 在 `web` 下运行现有单元测试和动效测试，补充 Dashboard 专属组件/状态测试。
2. 运行生产构建，记录并区分本次引入的问题与已有的 ESLint 警告。
3. 在本地浏览器检查桌面、平板宽度和移动宽度：首屏层级、表格滚动、刷新保留数据、空/错状态和 Dialog 开关。
4. 用键盘检查 Tab 顺序、Enter/Escape、焦点可见性和 Dialog 焦点回收。
5. 检查 `prefers-reduced-motion`，确认内容不依赖动画才能被理解。
6. UI 修改完成后，对本次变更涉及的 Dashboard 目标运行一次 Impeccable detector，并处理其中与本次范围相关的问题。

## 十一、明确不做的事情

- 不重写 Dashboard 的 API 或业务数据模型。
- 不新增没有产品确认的 KPI、趋势百分比、实时行情或假数据。
- 不把 Dashboard 改成全屏深色数据大屏。
- 不移除现有 table、筛选、分页、链接或 Dialog 编辑路径。
- 不引入轨道扫描场、中心雷达或持续高频背景动效。
- 不在本次工作中重做所有业务页面；其他页面只接受必要且兼容的共享组件视觉调整。

## 十二、规格确认记录

- 视觉方案：C. 混合升级。
- 视觉基调：深色科技外壳 + 高可读工作面。
- 信息层级：保留当前工作台页头、四项 KPI、两张图表、项目健康度表格和本周动态。
- 交互约束：保留 table Layout 与 Dialog 编辑习惯。
- 动效约束：轻量分层进入、数据变化反馈、刷新不清空、统一弹窗过渡、完整支持 reduced-motion。
