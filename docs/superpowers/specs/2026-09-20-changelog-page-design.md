# 功能更新 Changelog 页面设计

## 1. 背景与目标

当前系统已经有较完整的项目管理能力，并在近期持续加入财务、移动端、通讯录与协同能力，但用户目前无法在产品内直接了解这些变化。本次增加一个面向全体登录用户的「功能更新」页面，手动整理已有 git log，将产品演进按 V1 与 V2 两个阶段呈现。

目标：

- 在登录后的用户账号 hover 菜单中提供「功能更新」入口。
- 将「功能更新」放在「修改密码」上方，保留现有「退出登录」位置。
- 以用户能理解的产品语言展示已完成的重要功能，而不是直接暴露提交信息。
- 用 V1 / V2 体现产品能力演进，并默认展示当前推进中的 V2。
- 在桌面端保持信息密度，在手机端保持单列可读和触控友好。

非目标：

- 本次不做后台维护 changelog 的 CRUD。
- 本次不从 git log 运行时读取数据。
- 本次不增加权限判断；只要用户已经进入 dashboard 外壳，就可访问该页面。
- 本次不把每一个修复提交逐条展示，只呈现经过产品化归并的重点更新。

## 2. 现有项目约束

- 前端使用 Next.js 14 App Router，页面位于 `web/app/(dashboard)`。
- dashboard 外壳由 `web/app/(dashboard)/layout.tsx` 提供，账号菜单已经支持 hover、focus、tap、键盘方向键和 Esc。
- 视觉令牌集中在 `web/app/globals.css`，现有页面使用浅灰网格背景、白色内容面板、深蓝侧栏和品牌蓝强调色。
- 组件样式优先使用 CSS Modules；页面级重复卡片可使用已有全局 `.card`、`.btn-ghost` 等样式。
- 现有前端测试分为 `node:test` 单元测试和 Vitest DOM/组件测试，测试文件放在 `web/lib`。

## 3. 方案选择

采用「版本分段 + 日期时间线」方案。

### 选择理由

- 版本分段直接表达 V1 到 V2 的推进关系。
- 日期时间线能承载后续持续追加的更新，不会因为版本数量增加而变成拥挤的对比表。
- 默认打开 V2，符合当前产品仍在扩展与推进的状态。
- 移动端可以自然收缩为单列，不需要重排复杂的双栏布局。

### 放弃的方案

- 双栏版本看板：桌面端对比清晰，但手机端需要额外重排，且不适合按时间持续追加。
- 纯日期更新列表：实现简单，但无法突出 V1/V2 的产品阶段含义。

## 4. 信息架构

页面路由：

```text
/changelog
```

账号菜单顺序：

```text
功能更新
修改密码
退出登录
```

页面从上到下：

1. 页面标题区
   - 标题：`功能更新`
   - 说明：`记录每一次重要能力的上线与迭代。`
   - 辅助说明：`从项目管理基本盘，到财务与移动协同，持续推进。`
   - 右侧显示当前版本标识：`V2 · 当前版本`
2. 版本切换区
   - 两个可操作的分段按钮：`V1 基础项目管理`、`V2 扩展能力`
   - 默认选中 V2。
   - 切换不改变 URL，不引入额外数据请求。
3. 当前版本摘要
   - 版本名称。
   - 一句话定位。
   - 更新条目数量。
4. 日期时间线
   - 按日期倒序排列。
   - 每个日期下展示一个或多个更新条目。
   - 最近一组更新使用品牌蓝的轻量强调线。
   - 每个条目显示类型标签、标题和一段面向用户的说明。
5. 旧版本收束区
   - V1 切换后展示同样的结构。
   - 已完成阶段的视觉层级略弱于当前 V2，但内容仍清晰可读。

## 5. V1 / V2 内容口径

### V1：基础项目管理

V1 聚焦让团队完成项目运营的基本闭环：

- 工作台：项目健康度、项目进展、支出趋势和本周动态。
- 项目台账：项目创建、项目状态、年度筛选、负责人筛选、排序和基础操作。
- 进度跟踪：任务、里程碑、进度填报与逾期识别。
- 审批中心：项目、支出等关键动作的审批与结果通知。
- 支出记录与报表：支出登记、分类统计与报表查看。
- 账号与权限：用户登录、强制改密、角色权限与账号菜单。

### V2：扩展能力

V2 聚焦围绕项目管理基本盘的扩展：

- 财务能力：会计期间、财务规则、支出凭证、票据上传、凭证核实和审核状态流转。
- 移动端能力：PWA 外壳、底部 Dock、移动端卡片流、三态抽屉、下拉刷新与触控适配。
- 通讯录与协同：通讯录、部门人员信息、我的友商、人员与业绩合同信息。
- 附件能力：对象存储、业务目录、上传进度、拖拽/粘贴、失败分层与附件预览。
- 项目体验优化：客户字段、客户联系人、筛选与新建操作区、排序、删除与项目变更状态中文化。
- 体验与稳定性：统一品牌视觉、加载动效、窄屏适配、时间口径和审计日志展示优化。

### 版本条目数据

实现时新增一个只负责内容的静态模块，例如 `web/lib/changelog.ts`，提供明确的类型：

```ts
type ChangelogKind = "功能" | "优化" | "修复" | "移动端" | "财务";

interface ChangelogEntry {
  kind: ChangelogKind;
  title: string;
  description: string;
}

interface ChangelogDay {
  date: string;
  entries: ChangelogEntry[];
}

interface ChangelogVersion {
  id: "v1" | "v2";
  label: string;
  title: string;
  summary: string;
  days: ChangelogDay[];
}
```

日期使用 `YYYY-MM-DD` 作为稳定排序值，展示层格式化为 `YYYY.MM.DD`。数据按产品意义手动归并，不把 commit hash 或过程性提交暴露给用户。

## 6. 组件与交互设计

### 页面组件

新增页面组件负责三件事：

- 保存当前选中的版本状态。
- 根据选中版本渲染标题摘要与日期时间线。
- 为版本切换按钮提供可访问性状态。

建议拆分为以下边界，避免页面文件同时承载所有内容：

- `ChangelogPage`：状态和页面布局。
- `ChangelogVersionTabs`：版本切换。
- `ChangelogTimeline`：日期分组和条目渲染。
- `changelog.ts`：静态数据和类型。

如果页面规模不足以支撑独立组件，时间线和版本切换可以保留在页面文件中，但静态数据必须独立，便于后续维护。

### 版本切换

- 使用按钮而不是普通链接，避免产生不必要的路由跳转。
- 当前版本使用 `aria-selected="true"` 与清晰的视觉状态。
- 两个版本按钮位于同一 `role="tablist"` 中，版本内容区域使用对应 `role="tabpanel"`。
- 支持鼠标点击、键盘 Tab 和 Enter/Space。
- 不要求实现方向键切换；普通按钮的 Tab 顺序已经足够，避免引入与账号菜单不同的额外焦点模型。

### 菜单入口

- 在已有 `UserMenu` 中增加指向 `/changelog` 的 `Link`。
- 入口放在 `/change-password` 链接之前。
- 复用现有账号菜单的图标尺寸、菜单项样式和点击收起行为。
- 既有 hover/focus/tap/键盘行为不改变。

## 7. 视觉与响应式规则

- 页面沿用 dashboard 外壳，不新增独立的营销式 hero 或大面积装饰。
- 标题区使用紧凑的操作台排版，版本标识作为右侧状态信息，不做大号宣传文字。
- 时间线使用左侧日期列、中央细线/节点和右侧更新内容；在窄屏下日期列缩窄并转为上下结构。
- 条目使用白色面板或轻量分隔，不嵌套过多卡片。
- 标签颜色沿用现有状态色语义：品牌蓝用于功能、绿色用于财务/完成、琥珀用于优化、灰色用于修复或稳定性。
- 所有固定格式区域使用稳定的尺寸约束，避免标签、日期或标题换行造成布局跳动。
- `prefers-reduced-motion: reduce` 下关闭进入动画和切换位移动效，只保留状态变化。
- ≤767px：单列时间线、版本切换区允许横向滚动、更新内容占满可用宽度；菜单入口仍能通过触控打开。

## 8. 数据流与错误处理

本次页面只读取本地静态 changelog 数据，不发请求，因此不存在接口加载失败态。若静态数据为空或未来出现缺失版本，页面应提供明确的空态，而不是渲染空白区域。

账号菜单仍由 dashboard layout 管理；进入页面后继续沿用外壳的登录态校验、强制改密跳转和登出逻辑。

## 9. 测试与验收

### 自动化测试

新增或扩展测试覆盖：

- changelog 数据包含 `v1`、`v2`，且默认排序为 V2 在前、日期倒序。
- 页面默认显示 V2 标题与至少一条 V2 更新。
- 点击 V1/V2 可切换对应内容，且 `aria-selected` 只存在一个 true。
- 用户菜单按「功能更新、修改密码、退出登录」顺序渲染。
- 「功能更新」链接指向 `/changelog`，点击后菜单收起。
- 版本切换和时间线在窄屏下不依赖固定宽度，不出现水平溢出。

测试策略优先使用真实静态数据和真实 DOM，不为简单展示逻辑引入 mock。

### 手工/浏览器验收

- 桌面端打开账号 hover 菜单，确认入口位于修改密码上方。
- 点击入口进入 `/changelog`，默认显示 V2。
- 切换到 V1，再切回 V2，内容和选中态正确。
- 键盘 Tab 可以到达版本按钮，Enter/Space 可以切换。
- ≤767px 窗口检查页面单列、版本切换不被裁切、时间线不横向溢出。
- 检查浏览器控制台无新增错误。

## 10. 实施边界

本次实现只涉及：

- 一个静态 changelog 数据模块。
- 一个 `/changelog` dashboard 页面及其样式。
- dashboard 用户菜单新增一个入口。
- 相关自动化测试。

不修改后端 API、权限菜单契约、数据库、移动 Dock 导航和现有账号菜单交互模型。
