# 超级管理员与功能模块权限简化设计

日期：2026-09-30

## 背景与目标

当前系统把 `admin` 角色同时用于系统管理、全局项目数据范围、设备资产特权操作和财务管理；系统管理页面又允许把 `admin` 模块分配给普通账号。财务入口由账套成员关系控制，财务 API 进一步依赖账套级财务角色。权限散落在用户角色、模块和账套成员三处，难以直观回答“谁是管理员、用户能使用哪些模块”。

本设计将权限模型收敛为：

1. 全系统只有一个不可由用户管理 API 创建、编辑、停用或删除的超级管理员：系统初始化账号。
2. 超级管理员独占系统管理与原有全局管理能力；旧 `admin` 角色不再授予任何特权。
3. 普通用户不再配置角色，只由超级管理员分配可使用的功能模块；模块分配同时控制导航和对应后端 API。
4. 财务是一个普通功能模块。获得财务模块的用户可访问所有账套及财务模块中的全部操作，不再要求账套成员或账套级财务角色。
5. 项目参与范围、审批状态机、会计期间状态、凭证校验等业务规则继续生效；它们是业务约束，不是可配置的第二套用户权限。

## 决策与权限模型

### 超级管理员身份

- 在 `users` 表新增 `is_super_admin` 布尔字段，默认 `false`，由数据库部分唯一索引保证至多一条 `true` 记录。
- 迁移按 `api/seed.py` 的 `INITIAL_ADMIN_USERNAME` 将已存在的初始账号标记为超级管理员；`seed.main()` 对首次创建的初始账号也写入该标记。若部署数据已存在另一位超级管理员，唯一索引使迁移或 seed 失败，而不是静默产生两个超级管理员。
- 标记不是用户输入字段；创建用户、编辑用户和模块分配 API 不接受修改该字段。没有用户删除 API，本次不新增删除 API；初始账号的状态更新为 `disabled` 必须由后端拒绝。前端对超级管理员显示专属标记并隐藏停用操作。
- 登录防暴力的 `locked` 是安全锁定，不等同于管理员手工停用；现有锁定与自动解锁行为保持不变。超级管理员允许通过合法管理流程恢复为 `active`。
- 现有基于 `is_admin()` 的系统特权统一改为基于超级管理员标记。非初始账号即使遗留 `admin` 角色也不获得全局数据范围、系统管理、演示数据切换、资产特权操作或管理员专属项目操作。

### 功能模块与普通用户

- 可分配模块目录为：`opportunities`、`projects`、`assets`、`reports`、`contacts`、`partners`、`approvals`、`finance`。`admin` / “系统管理”不是可分配模块。
- 超级管理员可见全部可分配模块，并额外获得独立的系统管理入口。模块目录 API 不返回“系统管理”，用户模块 API 忽略或拒绝 `admin` 模块，普通用户无法通过模块分配获得系统管理能力。
- `/admin/*` 由后端超级管理员依赖统一保护，而非 `user_modules` 模块门禁。用户管理页前端门禁使用 `is_super_admin`。
- 普通用户没有任何角色配置入口。创建新用户默认显式分配空模块（只可访问始终开放的工作台、登录、身份/公共元数据等公共能力）；超级管理员再按需分配业务模块。
- 既有 `modules_assigned=true` 的用户保留原有有效业务模块，但移除 `admin`；未显式分配用户继续回落到当前四个基础模块 `opportunities/projects/assets/reports`，以避免升级后普通业务入口消失。历史 `admin` 角色映射不再是权限来源，并在迁移中移除非初始账号的 `admin` 角色关联。其他历史角色记录可保留作兼容数据，但不授予访问能力，也不再由系统管理页维护。
- `/meta/me/menus` 返回标准模块菜单、`is_super_admin` 和模块衍生的 `can_finance` / `can_approve`。系统管理菜单仅在超级管理员响应中作为不可分配的管理入口附加；前端继续用后端菜单和身份响应作为导航真相来源。
- 模块门禁在 API 层与菜单使用同一 `effective_modules()` 判定。项目、审批、附件等既有对象归属校验、状态机和写入校验保持不变。超级管理员仍保留现有全局业务操作能力。

### 财务模块

- 在后端模块目录加入 `finance`，路由 `/finance`；超级管理员拥有该模块，普通用户仅在显式分配后可访问。
- `/finance/*` 和 `/finance-accounting` 全部由 `MODULE_FINANCE` 路由门禁保护。去掉 `AccountBookMember` 查询和账套成员财务角色作为用户访问门槛；现有财务操作内的会计角色白名单也不再决定授权，拥有财务模块的用户具有同等财务模块操作权。
- 账套存在性、删除/回收状态、会计期间开闭、借贷平衡、凭证来源、单据状态和项目可见性等数据/业务校验不变。软删除账套仍不可作为活动账套使用。
- 财务页面从 `can_finance` 模块权限读取账套及模块数据；新建账套、恢复、回收、凭证与财务操作按钮改由财务模块权限控制，而非管理员身份或账套成员状态。
- 移除前端“成员与权限”管理入口和 `BookMembersDialog`；移除账套成员 CRUD API。`account_book_members` 历史数据及模型暂时保留，不再参与菜单、账套查询、模块访问或财务角色判定，避免本次不必要的数据删除。

## API 与数据迁移

- Alembic 新增单一后继迁移：增加 `users.is_super_admin NOT NULL DEFAULT false`，把唯一初始账号回填为 `true`，移除其他用户对 `admin` 角色的关联，删除显式用户模块中的 `admin` 项，并创建部分唯一索引 `uq_users_single_super_admin`（只约束 `is_super_admin IS TRUE`）。回滚移除索引和新列；角色/模块关联属于不可逆的语义收敛，downgrade 不重授旧管理权限。
- `api/seed.py` 创建或补齐初始管理员时确保标记为超级管理员；不要从 `admin` 角色推导此标记。
- `api/core/rbac.py`：用超级管理员字段判定 `is_admin`/`is_super_admin`；扩展模块目录、移除可分配 `MODULE_ADMIN`、加入 `MODULE_FINANCE`；普通用户模块仍以显式分配为准，既有未分配回落只包含四个基础模块。
- `api/routers/admin.py`：所有 `/admin/*` 接口只允许超级管理员；用户响应回带 `is_super_admin` 和有效模块；新用户默认显式空模块；拒绝用户角色写入、超级管理员身份写入，以及对超级管理员的停用请求；模块写入不允许 `admin`。
- `api/main.py` 与项目管理路由：新增财务模块路由门禁；系统管理和需超级管理员的特权端点使用超级管理员校验，清除对不可分配 `admin` 模块的依赖。
- `api/routers/meta.py`：按模块返回导航，附加超级管理员系统管理入口；财务可见性只由 finance 模块决定，不查询账套成员。
- `api/routers/finance.py` 与 `api/routers/finance_accounting.py`：账套与会计操作只校验功能模块和原有业务状态，不按 `AccountBookMember` 或 `finance_*` 角色作访问判断；移除账套成员 CRUD 路由。
- `web/lib/api.ts`、`web/lib/useMeta.ts`：增加超级管理员字段和 finance 模块类型/判定；删除财务成员 API 客户端；管理用户类型明确包含超级管理员标志。
- `web/app/(dashboard)/admin/page.tsx`、`UserDialog.tsx`：管理页以超级管理员身份门禁；移除只读角色页签/角色加载、用户角色列和角色选择；显示唯一超级管理员标记、保护停用入口；普通用户只分配功能模块；新用户默认空模块。
- `web/app/(dashboard)/finance/page.tsx`、`BookMembersDialog.tsx`、`finance/ArapPanel.tsx`：依据 finance 模块显示入口和可用操作；删除成员授权界面与角色专属前端分支。
- 更新受超级管理员语义影响的身份展示与权限 hook；`isAdmin` 等旧 hook 名如暂时保留，返回值必须只源于 `is_super_admin`，不能再源于 `admin` 角色。

## 安全与错误行为

- 非超级管理员请求任一 `/admin/*` 均稳定返回 403，即使请求手工提交 `roles: ["admin"]`、`modules: ["admin"]` 或 `is_super_admin: true`。
- 对超级管理员 `PATCH status=disabled` 返回 400 或 409 的明确中文错误；数据库唯一索引负责阻止第二名超级管理员写入。创建和编辑 API 不允许改变该标记。
- 未获 `finance` 模块的账号访问任一财务路由稳定返回 403；获得 finance 模块后可以访问任一未软删除账套，不受历史成员行或账套角色影响。
- 迁移不得将旧账套成员记录自动转换成 finance 模块，因为那会把某个账套的旧授权扩大为全部账套权限。所有普通账号由超级管理员显式分配财务模块。
- 移除财务成员 CRUD 后，旧客户端不再具有创建、变更或撤销账套成员授权的入口；成员表数据保留但不具授权含义。

## 验收标准

### 后端

- 数据库中 `is_super_admin=true` 最多一条；迁移只把初始账号设为超级管理员；seed 幂等且不会从旧 `admin` 角色提权。
- 超级管理员可访问系统管理；旧 `admin` 角色用户不可访问系统管理、全局数据或管理员特权接口。
- 任何普通用户 API 请求均不能获得或改写超级管理员身份；超级管理员不可通过用户状态接口停用；删除 API 不存在。
- 新用户默认为空模块；分配 `admin` 无法开放系统管理；既有显式业务模块和旧账号默认四基础模块按设计迁移。
- 菜单项、`can_approve` 和每个受保护模块 API 一致；系统管理只向超级管理员返回。
- 未分配 finance 返回 403；分配后无账套成员记录也能访问每个活动账套及模块操作；旧账套成员角色不能限制、扩大或撤销该访问；停用/回收账套、关闭期间、凭证合法性等业务校验仍有效。
- 数据库迁移支持从当前 `0033_project_receivable_updaters` 升级至新 head；升级/回滚测试确认新标记、单一唯一性和历史模块数据处理。

### 前端

- 管理页只有超级管理员能看到；用户列表清晰标记唯一超级管理员且无停用按钮，普通用户状态仍可启用/停用。
- 用户创建/编辑仅配置功能模块，不出现角色页签/角色选择；新用户初始不勾选任何模块；系统管理不出现在可分配目录。
- 财务入口按 finance 模块显示；获得模块的普通用户可以选择所有活动账套及使用相同财务功能；用户看不到“成员与权限”入口或财务角色配置。
- 超级管理员身份展示、项目/资产等管理员特权按钮仍只对超级管理员可见；普通用户模块导航正常。
- 前端 Vitest/Node 单测、TypeScript、生产 build 与后端数据库测试通过；迁移 upgrade/downgrade 及 `git diff --check` 通过。

## 范围外

- 不删除历史 `roles`、`user_roles` 或 `account_book_members` 表，也不迁移账套成员授权为功能模块。
- 不重新设计各业务模块的对象级数据范围、项目负责人/成员协作、审批流、会计状态机和数据校验。
- 不增加超级管理员转让、超级管理员恢复、用户永久删除或批量模块模板等功能。
- 不改写系统全部角色数据与角色表结构；角色相关用户权限设置界面和写入能力退出当前产品路径，遗留非 admin 角色映射只作为无授权效力的兼容数据。
