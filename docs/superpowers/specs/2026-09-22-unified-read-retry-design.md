# 统一数据读取后台恢复设计

## 背景

当前前端已经在 `web/lib/useAsyncData.ts` 中为部分页面提供了读取失败后的后台恢复能力，策略集中在 `web/lib/readRetry.ts`。但工作台、审批中心、项目详情、通知、全局元数据和部分弹窗仍有手动读取逻辑，遇到临时网络或网关故障时可能直接进入页面错误状态。

本设计将所有 JSON 数据读取统一到同一套 retry 机制中，让不同页面遵守相同的恢复语义；文件传输和写入操作继续保持一次性请求，避免重复传输或重复修改。

## 目标

- 所有 JSON 数据读取请求统一支持无感后台 retry。
- 前 5 次补偿请求均在约 1 秒内发起，之后按指数退避增加间隔。
- 已有数据在临时读取失败期间继续展示，不清空、不弹错误。
- 首次读取失败时保持加载状态，后台持续恢复，不立即展示网络错误。
- 网络恢复、页面重新获得焦点或回到前台时可以立即唤醒一次 retry。
- 请求取消、页面卸载、项目或筛选条件变化时，不留下旧请求和定时器。
- 业务错误、会话错误、权限错误和资源不存在不进入无限 retry。
- 写入、上传、下载、图片预览、PDF 预览和文件导出不进入本机制。

## 不在范围内

- 不在 FastAPI 服务端增加所有请求的自动重放。
- 不修改数据库事务、SQL 重试或业务状态机。
- 不为附件下载、图片/PDF 预览、导出文件增加后台无限 retry。
- 不自动重放 `POST`、`PUT`、`PATCH`、`DELETE` 或 XHR 上传。
- 不引入全局数据缓存或改变现有缓存失效策略。

## 用户可见契约

### 暂时性读取错误

以下错误视为“服务可能很快恢复”：

- 网络连接失败、DNS/连接异常；
- HTTP `408`、`425`、`429`、`500`、`502`、`503`、`504`。

处理方式：

- 有旧数据时保留旧数据；
- 清空页面级错误文案；
- 不弹 Toast 或错误横幅；
- 继续在后台重试；
- 成功后自动替换为最新数据。

### 不可恢复或需要用户处理的错误

- `400`：参数或请求内容错误，立即展示错误；
- `401`：继续执行现有会话清理和登录跳转；
- `403`：立即展示无权限；
- `404`：立即展示资源不存在；
- `AbortError`：静默结束，不更新页面状态。

不可恢复错误不会触发无限 retry，也不会把旧筛选条件下的数据伪装成当前结果。依赖变化时由页面状态层按照现有 `resetOnDepChange` 语义决定是否清空旧数据。

## 方案

采用“统一读取运行器 + 页面状态适配”的两层结构。

### 统一读取入口

在 API 传输层拆分一次性请求和读取请求：

```text
JSON GET / HEAD       → readRequest / runReadWithRetry → 自动 retry
POST / PUT / PATCH / DELETE → requestOnce → 失败立即返回
文件、Blob、对象 URL 请求 → requestOnce → 不自动 retry
XHR 上传               → apiUploadWithProgress → 不自动 retry
```

现有 `apiGet` 和 `apiGetScoped` 作为 JSON 读取 API 的统一入口，内部改为调用 `runReadWithRetry`。当前一次性传输函数重命名为 `requestOnce`（或提取为同等职责的内部函数），供 `apiGet` 和写入/文件入口分别调用。现有 `apiPost`、`apiPut`、`apiPatch`、`apiDelete`、上传和文件函数继续使用一次性请求。

读取入口必须只接受无副作用的 GET/HEAD 读取调用；文件请求即使底层 HTTP 方法也是 GET，也必须明确留在文件入口，不能因为方法相同而被自动纳入 retry。

### 读取策略模块

保留 `web/lib/readRetry.ts` 作为无 React 的纯策略模块，集中提供：

- 可重试状态集合；
- `isRetryableReadError(error)` 错误分类；
- `getReadRetryDelay(attempt, random?)` 退避计算；
- 供读取运行器使用的可取消等待参数和事件唤醒协议。

错误分类不能依赖页面组件；`HttpError`、`NetworkError` 和 `AbortError` 的判定在读取层统一完成。`readRetry.ts` 不反向导入 `api.ts`，而是依赖稳定的错误字段和错误名称：`HttpError` 提供数值 `status`，网络错误提供稳定的 `name`，取消错误统一按 `AbortError` 判断，从而避免模块循环依赖。

### 读取运行器

新增或整理一个框架无关的 `runReadWithRetry<T>`，职责是执行单个 JSON 读取任务：

1. 使用调用方提供的 `AbortSignal` 发起一次读取。
2. 成功后直接返回结果。
3. 遇到暂时性错误时计算下一次延迟并等待。
4. 等待期间监听取消信号；取消后立即结束，不再发起请求。
5. 页面重新联网、重新获得焦点或回到前台时，取消当前退避并立即发起一次补偿读取。
6. 对同一个运行器始终保持至多一个在途请求和一个等待定时器。
7. 暂时性错误不会向调用方 reject；只有成功、不可恢复错误或主动取消会结束本次任务。

retry 没有固定次数上限，只要任务仍被页面或全局缓存持有就继续恢复；延迟上限和抖动保证不会形成高频忙等。页面卸载或资源依赖变化时必须取消整个运行器。

## 退避策略

`attempt` 从第一次失败后的第 1 次补偿请求开始计数：

| 补偿请求 | 基准间隔 | 实际范围 |
|---|---:|---:|
| 第 1～5 次 | 1000ms | 800～1200ms |
| 第 6 次 | 2000ms | 1600～2400ms |
| 第 7 次 | 4000ms | 3200～4800ms |
| 第 8 次 | 8000ms | 6400～9600ms |
| 第 9 次 | 16000ms | 12800～19200ms |
| 第 10 次及以后 | 30000ms | 24000～30000ms |

默认使用 ±20% 随机抖动。测试可以传入固定随机值，确保延迟序列确定。若服务端对 `429` 或 `503` 返回有效的 `Retry-After`，读取运行器优先遵守服务端建议；客户端自行计算的等待最多为 30 秒，服务端明确给出的等待最多采用 60 秒，避免异常响应让客户端进入无限长的单次等待。

## 页面状态适配

### `useAsyncData`

`useAsyncData` 继续保持现有公开字段和调用签名，成为页面读取状态的标准适配器：

- `data`：成功前保留当前数据；
- `firstLoad`：仅表示没有任何可展示数据且正在首次读取；
- `loading`：表示当前读取任务仍未结束；
- `error`：只承载不可恢复错误；
- `reload`：取消旧任务、重置 retry 计数并重新读取；
- `setData`：保留现有局部更新能力。

页面渲染骨架必须依据 `firstLoad`，不能仅依据 `loading` 把已经有数据的页面替换成整页骨架。已有数据在后台 retry 时保持可见，可以仅保留轻量的刷新状态。

现有 `useAsyncData` 不再维护第二套 retry 定时器；它负责启动/取消由 `apiGet` 返回的读取 promise，并维护数据、`firstLoad`、`loading` 和最终错误状态。所有生产 JSON loader 都通过 `apiGet`/`apiGetScoped` 进入 `runReadWithRetry`。框架无关的读取运行器单测负责网络失败、取消和恢复行为，Hook 测试负责页面状态行为。

### 全局缓存读取

`web/lib/useMeta.ts` 中的用户、菜单、部门读取继续保留缓存和 inflight 去重，但底层读取改为使用统一运行器：

- 同一会话的并发调用共享同一个 inflight promise；
- 临时错误期间不清除已有身份快照或已缓存菜单；
- `401` 仍触发会话清理；
- 退出登录时继续清空缓存和取消相关读取。

### 手动读取页面和组件

以下现有手动读取场景需要统一到 `useAsyncData`；无法直接由 React Hook 持有生命周期的全局缓存读取统一调用 `runReadWithRetry`：

- 工作台 summary/weekly；
- 审批待办；
- 项目详情及其数据聚合读取；
- 通知数量和通知列表；
- 项目选择器、联系人/合作方/费用等抽屉和弹窗详情；
- 其他通过 `useEffect` + `try/catch` 直接维护 `loading/error/data` 的 JSON 读取。

`Promise.all` 聚合读取必须保持每个 JSON loader 经过 `apiGet`/`apiGetScoped`；不能在 retry 之前用 `.catch(() => null)` 把网络错误吞掉。可选数据只有在统一读取层完成不可恢复失败后，才允许按既有业务语义降级为 `null`。

## 接入盘点

当前 `web/lib/api.ts` 中的 JSON 读取主要通过 `apiGet` 和 `apiGetScoped`，这两个入口覆盖财务、项目、任务、联系人、合作方、通知、审批、报表和管理数据等 API。直接调用内部 `request` 的路径目前主要是下载文件和创建对象 URL，应保持排除。

实施时还要对页面层做一次静态盘点，重点搜索：

- `useEffect` 中的 `load`/`reload` 函数；
- `apiGet`、`apiGetScoped` 之外的 JSON 读取；
- `.catch(() => null)`、`.catch(() => [])` 等可能吞掉临时读取错误的逻辑；
- 仅使用 `loading` 而没有区分 `firstLoad` 的页面。

盘点结果以测试和代码审查为准，不把文件传输入口纳入读取 retry 清单。

## 测试设计

### 策略单元测试

- 网络错误和 `408/425/429/500/502/503/504` 可重试；
- `400/401/403/404` 和普通业务错误不可重试；
- 前 5 次延迟在约 1 秒范围内；
- 后续延迟为约 `2/4/8/16/30` 秒并封顶；
- 随机抖动始终在合法范围内；
- 有效 `Retry-After` 被遵守且受上限保护。

### 读取运行器测试

- 前 5 次失败后恢复，最终只返回一次成功结果；
- 暂时性错误不会提前 reject；
- 不可恢复错误立即 reject 且不继续请求；
- 等待期间 AbortSignal 取消后没有后续请求；
- online/focus/visibilitychange 会唤醒一次等待中的 retry；
- 同一运行器不会出现并发请求或多个定时器；
- 长时间失败时按封顶间隔继续恢复，不出现忙循环。

### Hook 和页面状态测试

- 已有数据遇到临时错误时数据不变、错误为空；
- 首次读取失败时保持 firstLoad，不展示网络错误；
- 读取成功后替换旧数据并结束 loading；
- 依赖切换、手动 reload 和卸载会取消旧读取；
- 非恢复错误仍能进入现有错误展示；
- 工作台、审批、项目详情和通知等手动读取场景至少各有一个回归测试。

### 请求边界测试

- 所有 `apiGet`/`apiGetScoped` JSON 请求进入读取运行器；
- `POST/PATCH/DELETE` 只调用一次；
- 上传、下载、Blob、图片/PDF 预览不进入读取运行器；
- API 读取入口不会因为 `raw=true` 或文件路径而自动重试。

## 验收标准

- 所有 JSON 数据读取通过统一入口获得相同 retry 策略。
- 网络抖动时已有页面数据不消失、不弹错误、不要求用户点击重试。
- 前 5 次补偿请求约每秒一次，随后逐步增加并封顶。
- 后台恢复后页面自动显示最新数据。
- 401、403、404、400 等明确错误仍保持原有业务处理。
- 写入和文件操作没有被自动重放。
- 页面切换和卸载后不存在旧请求、旧 timer 或旧响应覆盖新状态。
- 相关单元测试、Hook 测试、前端测试和生产构建通过。

## 风险与取舍

- 无限恢复会在后端长时间不可用时持续产生低频读取流量，因此使用 30 秒封顶、随机抖动和页面生命周期取消；不会创建脱离页面的全局后台任务。
- 读取层要求 JSON GET/HEAD 接口无副作用；若未来出现“GET 会修改状态”的接口，必须显式排除，不能仅按 HTTP 方法判断。
- 全面接入需要改造少量手动读取页面，但换来的结果是所有页面共享同一套行为，避免后续新增页面再次遗漏 retry。
