## 2. 测试结论

本轮使用 10 个并发虚拟用户，持续执行真实的只读浏览流程。每个虚拟用户按「当前用户 → 菜单权限 → 字典 → 工作台 → 项目台账 → 项目详情 → 进度 → 任务 → 成本 → 报表 → 通知」的顺序循环访问，并在每次请求后等待 1 秒，模拟用户阅读和点击间隔。

测试持续 60 秒，共完成 517 次只读 API 请求，实际吞吐为 8.43 RPS，所有请求均成功，未出现 HTTP 4xx、HTTP 5xx、超时或网络错误。

本轮结果表明：

- 10 个虚拟用户同时浏览时，核心只读链路整体稳定。
- 总体成功率为 100%。
- 所有接口 P95 均低于 600 ms。
- 项目详情、项目跟进、任务列表属于相对较慢的接口，P95 约为 573～575 ms。
- 当前用户、部门字典和任务列表出现了约 2.3～2.4 秒的 P99 长尾，但没有请求失败。
- 本轮没有调用创建、修改、删除、审批、上传或导入接口，不代表写入型业务在并发下的表现。

**本轮 10 用户只读场景判定：通过。**

该结论表示系统在本次 10 个虚拟用户、60 秒、只读浏览模型下运行稳定，不代表已经完成最大容量或极限压力验证。

## 3. 测试模型

### 3.1 虚拟用户行为

每个虚拟用户独立运行以下访问流程：

1. 读取当前用户信息；
2. 读取菜单权限；
3. 读取用户和部门字典；
4. 打开工作台并读取汇总数据；
5. 读取本周动态；
6. 读取通知数量；
7. 打开项目列表和项目选择器；
8. 打开一个项目详情；
9. 读取项目进度和跟进记录；
10. 读取任务列表；
11. 读取支出列表；
12. 读取成本报表；
13. 返回流程起点并继续循环。

每次请求完成后等待 1 秒，作为页面阅读、点击和下一步操作的模拟时间。

### 3.2 认证模型

- 测试开始时登录 1 次。
- 压测阶段复用同一个 Bearer Token。
- 没有让 10 个虚拟用户反复调用登录接口。
- 这样可以避免把登录审计、密码校验和用户状态更新误当作普通页面浏览流量。

因此，本次是「10 个并发浏览用户」的 API 级模拟，不是 10 个独立账号，也不是 10 个真实浏览器进程。

## 7. 性能分析

### 7.1 正向结果

1. **并发稳定性良好**：10 个虚拟用户持续 60 秒访问，517 次请求全部成功。
2. **总体延迟可接受**：所有接口 P95 均低于 600 ms，核心列表接口 P95 大多在 223～286 ms。
3. **聚合接口没有出现明显失败**：工作台汇总和成本报表在本轮中分别达到 242 ms 和 267 ms 的 P95。
4. **没有观察到服务端错误外显**：未出现 4xx、5xx、超时或网络连接异常。

### 7.2 需要关注的长尾

以下接口在 P99 出现了 2 秒以上的偶发长尾：

| 接口 | P95 | P99 | 关注点 |
| --- | ---: | ---: | --- |
| 当前用户 | 591 ms | 2,428 ms | 偶发鉴权、数据库读取或服务器调度延迟 |
| 部门字典 | 222 ms | 2,350 ms | 偶发字典查询或连接等待 |
| 任务列表 | 575 ms | 2,359 ms | 任务查询、权限范围过滤或数据库排队 |

这些长尾没有造成请求失败，但如果用户规模继续上升，可能会进一步放大为页面等待或超时。建议在下一轮测试中配合 PostgreSQL 活跃连接、锁等待和服务器 CPU、磁盘 I/O 监控进行定位。

## 8. 前端与测试范围说明

本轮通过前端实际页面所对应的 API 路径模拟用户浏览链路，覆盖了工作台、项目台账、项目详情、进度、成本和通知等核心数据请求。

但本轮不是浏览器级压测，未直接测量：

- 10 个真实浏览器实例的页面渲染；
- Next.js 静态资源并发加载；
- DOM 点击耗时；
- 浏览器内存和 JavaScript 主线程占用；
- Core Web Vitals，例如 LCP、INP 和 CLS；
- 移动端浏览器的网络和渲染表现。

因此，本报告的性能数据主要代表「API + FastAPI + PostgreSQL」只读链路，不能直接等同于 10 台浏览器的完整前端体验指标。

## 9. 环境监控限制

本轮结果来自压测端 HTTP 统计，没有同步采集生产服务器内部资源曲线。因此当前不能仅凭本报告确认：

- API 进程 CPU 是否接近上限；
- PostgreSQL 连接池是否出现等待；
- 数据库是否发生锁等待；
- 磁盘 I/O 是否出现瞬时拥塞；
- 应用容器内存是否持续增长；
- 请求结束后资源是否完全回落。

建议下一轮测试时同步执行：

```bash
docker stats
vmstat 1
iostat -xz 1
```

PostgreSQL 建议记录活跃连接、等待事件、锁等待、慢查询、临时文件和缓存命中率。

## 10. 后续建议

建议继续按照梯度增加负载，而不是直接进行无限制压力攻击：

| 阶段 | 虚拟用户 | 思考时间 | 持续时间 | 目的 |
| --- | ---: | ---: | ---: | --- |
| 当前轮次 | 10 | 1 秒 | 60 秒 | 验证多人只读浏览稳定性 |
| 下一轮 | 20 | 1 秒 | 60 秒 | 观察并发翻倍后的响应和数据库连接 |
| 第三轮 | 30 | 1 秒 | 60 秒 | 寻找 P95、P99 和错误率拐点 |
| 稳定性轮 | 10～20 | 1 秒 | 30～60 分钟 | 观察内存、连接和资源泄漏 |

每一轮建议设置以下停止条件：

- HTTP 5xx 大于 1%；
- 连续出现请求超时；
- P95 持续超过 2 秒；
- PostgreSQL 连接持续耗尽或出现明显锁等待；
- CPU 持续超过 85%；
- 内存持续增长或开始使用 Swap；
- 真实用户反馈页面无法正常使用。

写入型压测应另行设计，使用专用测试项目、专用账号和明确的清理方案，不应在生产环境随机执行真实业务写操作。

## 11. 最终判定

**测试结论：10 个并发虚拟用户的只读浏览场景通过。**

在 60 秒测试期间，系统完成 517 次只读请求，实际吞吐 8.43 RPS，成功率 100%，无 HTTP 错误、超时或网络异常；所有接口 P95 小于 600 ms。

**风险结论：存在少量 P99 长尾，需要继续观察。**

当前用户、部门字典和任务列表的 P99 约为 2.3～2.4 秒。该长尾尚未影响成功率，但在 20～30 个并发用户或更长时间运行时可能进一步放大。

**容量结论：暂不判定最大承载能力。**

本轮已经验证 10 个虚拟用户的只读使用场景，但尚未完成更高用户数、服务器资源监控、真实浏览器并发和写入型业务场景测试。
