当前这套「青色 + 蓝色」，问题不在选色，在
颜色被分配了太多职责

我把 web/app/globals.css 的深浅两套令牌逐条算了一遍对比度、色相与明度，再对着工作台里实际用到颜色的地方看。 结论是：信号青、品牌青、图表主系列、焦点环、链接、选中态全部指向同一个令牌，于是它必须同时“够亮、够醒目、够专业”，结果只能越调越电光； 外加荧光青柠当行动色，两个高亮色互相抢戏。审计还量出两件事：深浅两套主题里 8/8 个同名令牌的浅色明度都更低（平均 −30.4pp），且深色下 8/8 个彩色的 HSL 饱和度都是 100% —— 所以它不是「一套主题的两档」，而是两套皮肤。下面四套方案都按同一套语义职责重排，差别只在「用什么气质承载信号」。

5 → 0–3
深色下同时处于“高亮档”（L > 72 且彩度 > 0.09）的语义角色数。现状是品牌、行动、完成、警告、危险五个一起亮，界面没有主次；新方案只让必要的角色亮。
30° → 41–65°
图表系列色之间（OKLCH 色相）的最小间距。现状品牌青与数据蓝只差 53°、青与水绿只差 31°，两条线在深色底上几乎分不开 —— 这是“青和蓝搭在一起不好看”的技术原因，不是审美问题。D 保留现有色相，所以这项仍是 30°，它靠拆职责而不是改色相解决。
233 个引用点
--brand 在 web/ 里的直接引用 117 处 + 经 9 个别名消费 116 处，横跨 30 个文件、9 类语义（链接 / 焦点环 / 输入框边框 / 选中底 / 进度条 / 图表系列 / 导航强调 / 告警三级 / 登录信号）。一个颜色背这么多职责，只能越调越亮。

同一组指标，同一套算法；数字不达标的格子标红

结构指标

OKLCH 色相 / WCAG 2.1 对比度

读法：D 的「共用 4 个角色」是设计选择而不是缺陷 —— 它整套只留一个强调色，主次靠填充 / 描边 / 文字三种形态区分； 其余方案的共用是对同一色值的无意复用（如现状把 --done 直接等于 --action）。 两种做法都能成立，区别在于「减色」还是「分职」。

07

怎么落地

令牌名与现状一致，替换值即可，不需要改组件

STEP 1

先拆职责，再换色

把 --done 从 --action 里拆出来（现状深色两者都是 #c6ff72），--data-* 与 --brand 解耦，新增 --control-border 深色分支。只这一步就能消掉「完成态和主按钮一个颜色」和输入框看不见边界两个问题。

STEP 2

换令牌值（两处）

只改 globals.css 的 :root 与 :root[data-theme="light"] 两块；组件层本来就用 var()，不需要动。守卫 avColorTokens / avSourceGuard 里的色值与对比度断言要一起更新。

STEP 3

按截图比对再收

用 scripts/av-acceptance-catalog.mjs 出 1440 / 1280 / 900 / 390 × 深浅两套图，重点是表头、徽标、图表系列与输入框边界；主题切换要逐令牌等价（同一色相，只变明度与彩度）。
